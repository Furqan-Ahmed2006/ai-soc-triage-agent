**Sentinel-LogiX** is an AI-powered security log investigation platform that helps security analysts and engineering teams investigate suspicious activities in uploaded JSON and JSONL security logs.

Built around a genuine **Model Context Protocol (MCP) client-server architecture** and a **LangGraph-based agentic workflow**, the system dynamically discovers and invokes security investigation tools, correlates events, evaluates risks using deterministic Python rules, and generates evidence-grounded investigation reports.

Rather than relying entirely on LLM-generated conclusions, Sentinel-LogiX separates deterministic security analysis from AI reasoning to improve transparency, reliability, and auditability.

## 🎯 Problem Statement

Security teams frequently work with large volumes of raw logs generated by authentication systems, APIs, networks, and applications.

Investigating these logs manually can be time-consuming, especially when identifying relationships between events across different sources.

Using general-purpose LLM interfaces directly on raw security logs also introduces several challenges:

- **Hallucinated Evidence:** LLMs may generate conclusions that are not supported by the available log data.
- **Unreliable Risk Assessment:** Models may assign arbitrary severity levels or incorrectly interpret unknown indicators of compromise (IOCs).
- **Log-Based Prompt Injection:** Malicious instructions embedded in untrusted log fields can influence model behavior.
- **Limited Investigation Traceability:** Ad-hoc tool execution can make it difficult to understand which data was retrieved and how conclusions were reached.
- **Manual Event Correlation:** Analysts may need to inspect multiple events manually to identify suspicious sequences and relationships.

## 💡 Solution

Sentinel-LogiX provides an AI-assisted investigation workflow that processes uploaded security logs and uses MCP-powered tools to investigate suspicious activity.

Its core design principle is:

**Deterministic security analysis for measurable results, combined with LLM reasoning for adaptive investigation and understandable explanations.**

### Key Features

#### 1. Security Log Upload & Normalization
- Supports `.json` and `.jsonl` security log files.
- Validates uploaded files, record counts, and JSON structure.
- Normalizes different log schemas into a unified security event format.
- Maintains isolated SQLite session stores for individual investigations.

#### 2. Genuine MCP Client-Server Architecture
- Implements a standalone custom MCP server using the official Python MCP SDK.
- Uses standard MCP `stdio` transport.
- Implements an MCP client that discovers available tools through `list_tools()`.
- Executes tools through the MCP protocol using `call_tool()`.
- Maintains a clear separation between the agent host and security data tools.

#### 3. LangGraph-Based Agentic Investigation
- Uses LangGraph to orchestrate multi-step security investigations.
- Dynamically selects tools based on investigation findings.
- Retrieves additional evidence when suspicious activity is discovered.
- Supports conditional investigation paths rather than relying entirely on a fixed sequence.
- Identifies telemetry gaps and unsupported capabilities instead of inventing missing evidence.

#### 4. Deterministic Risk Engine
- Calculates weighted risk scores between `0–100`.
- Assigns severity levels: `Low`, `Medium`, `High`, and `Critical`.
- Evaluates security events through auditable Python rules.
- Keeps unknown IOCs unverified instead of automatically treating them as safe or malicious.
- Separates risk calculation from LLM-generated explanations.

#### 5. Multi-Layer AI Security Guardrails
- Detects suspicious prompt-injection patterns in user inputs.
- Treats retrieved log content as untrusted data.
- Applies protections against embedded log-based prompt injection.
- Enforces investigation session isolation.
- Includes automated security and workflow evaluation checks.

#### 6. Investigation Traceability & Reporting
- Displays MCP tool execution traces.
- Records investigation activity for auditability.
- Generates structured security investigation reports.
- Supports exporting investigation reports as `.docx` files.
- Provides session cleanup functionality for uploaded data.

## 🔄 How It Works

The application follows a multi-stage investigation workflow.

| Stage | Operation |
|---|---|
| 1. Upload | User uploads JSON or JSONL security logs. |
| 2. Processing | Files are validated, parsed, and normalized. |
| 3. Storage | Normalized events are stored in an isolated SQLite session database. |
| 4. MCP Discovery | The MCP client discovers available investigation tools. |
| 5. Investigation | The LangGraph agent selects and invokes relevant MCP tools. |
| 6. Correlation | Related events are retrieved and correlated to establish activity timelines. |
| 7. Risk Evaluation | The deterministic risk engine calculates risk based on configured rules. |
| 8. Reporting | The LLM generates an evidence-grounded investigation report. |

### Example Investigation Scenario

Consider an uploaded authentication log containing:

1. Multiple failed login attempts against an administrator account.
2. Repeated attempts originating from the same IP address.
3. A successful login following the failed attempts.

The agent can investigate this sequence by:

- Searching for failed authentication events.
- Retrieving activity associated with the source IP.
- Checking subsequent activity associated with the targeted account.
- Correlating related events into a timeline.
- Evaluating risk using deterministic rules.
- Generating an investigation report with supporting evidence and recommended next steps.

The system distinguishes observed evidence from assumptions and reports unavailable information as a telemetry gap.

## 🔌 MCP Investigation Tools

The custom MCP server exposes six security investigation tools:

| Tool | Description |
|---|---|
| `search_security_events` | Searches uploaded security events using supported filters. |
| `get_event_details` | Retrieves detailed information about a specific event. |
| `get_ip_activity` | Retrieves security activity associated with a source IP. |
| `get_user_activity` | Retrieves security activity associated with a username. |
| `correlate_security_events` | Identifies relationships between events and builds investigation context. |
| `evaluate_risk` | Executes deterministic risk evaluation for relevant evidence. |

The agent does not rely on a hardcoded Python tool dispatcher. It communicates with the MCP server through the MCP client-server protocol, discovers available tools, and invokes them through the protocol.

## 🧠 Agentic Workflow

The investigation agent is orchestrated using LangGraph.

Its workflow supports:

- Investigation state management.
- Dynamic tool selection.
- Conditional routing based on retrieved evidence.
- Multi-step tool execution.
- Evidence collection and correlation.
- Risk evaluation.
- Final report generation.

The agent can pursue different investigation paths depending on what the uploaded logs reveal.

For example, discovering repeated failed logins followed by a successful login can trigger further investigation into the affected account and its subsequent activity.

## 🔐 Security & Reliability

Security is an important part of Sentinel-LogiX's design.

| Security Measure | Purpose |
|---|---|
| File validation | Restricts malformed and oversized uploads. |
| Record limits | Controls resource consumption during processing. |
| Session isolation | Separates uploaded datasets and investigations. |
| Prompt injection defenses | Reduces the risk of malicious instructions embedded in logs influencing the agent. |
| Deterministic risk scoring | Prevents the LLM from independently inventing numerical risk scores. |
| Unknown IOC handling | Keeps unverified indicators explicitly unverified. |
| MCP execution trace | Provides visibility into tool discovery and execution. |
| Audit logging | Supports investigation traceability. |
| Session cleanup | Allows uploaded investigation data to be deleted. |

**Operational limitation:** Sentinel-LogiX is an investigation and advisory system. It does not automatically block IP addresses, quarantine endpoints, or perform destructive containment actions.

## 🧪 Evaluation & Testing

Sentinel-LogiX includes an automated evaluation suite in `evaluate_guardrails.py`.

The suite contains nine checks covering security, MCP communication, and risk evaluation.

The evaluation focuses on validating areas such as:

- Prompt-injection defenses.
- Untrusted log handling.
- MCP tool discovery and invocation.
- Session isolation.
- Deterministic risk evaluation.
- Unknown IOC handling.
- Evidence and capability-gap reporting.

Run the evaluation suite locally:

## 🚀 Getting Started

### Prerequisites

- Python 3.10 or later.
- A Groq API key.
- Git.

### 1. Clone the repository

```bash
git clone https://github.com/Furqan-Ahmed2006/ai-soc-triage-agent.git

cd https://github.com/Furqan-Ahmed2006/ai-soc-triage-agent
```

### 2. Create a virtual environment

**Windows:**

```bash
python -m venv .venv

.venv\Scripts\activate
```

**Linux / macOS:**

```bash
python -m venv .venv

source .venv/bin/activate
```

### 3. Install dependencies

```bash
pip install -r requirements.txt
```

### 4. Configure environment variables

Create a `.env` file in the project root:

```env
GROQ_API_KEY=your_groq_api_key_here
```

Never commit your actual API key or other credentials to GitHub.

### 5. Run the evaluation suite

```bash
python evaluate_guardrails.py
```

### 6. Launch the application

```bash
streamlit run app.py
```

The application will be available at:

```text
http://localhost:8501
```

## 🔒 Privacy & Operational Notes

- Uploaded logs may contain sensitive information such as usernames, IP addresses, tokens, and internal system details.
- Uploaded data is processed in isolated investigation sessions.
- Session data can be deleted through the application.
- LLM-based analysis requires sending relevant information to the configured Groq API. Users should avoid uploading sensitive production logs unless they have permission and have reviewed their data-handling requirements.
- The system is advisory-only and does not execute automatic destructive security actions.
- Investigation results depend on the quality, completeness, and supported schema of the uploaded logs.
